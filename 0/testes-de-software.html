Qualidade

Verificação × Validação

Verificação

Estamos construindo o produto corretamente?

Compara o software com especificações, regras e critérios definidos.

Exemplos: revisão, análise estática e testes automatizados.

Validação

Estamos construindo o produto certo?

Confere se a solução atende à necessidade real de quem vai usá-la.

Exemplos: aceite, demonstração e avaliação com usuários.

Testes ajudam na verificação e podem apoiar a validação, mas não substituem a conversa sobre o problema.

Vocabulário

Níveis e tipos de teste

Unitário: uma função ou unidade isolada.

Integração: componentes colaborando, como serviço e banco.

Sistema / ponta a ponta: fluxos completos do sistema.

Aceitação: critérios e necessidades de negócio.

Funcional: comportamentos e regras do produto.

Não funcional: desempenho, segurança, acessibilidade e confiabilidade.

Regressão: comportamentos existentes continuam funcionando.

Caixa-preta / caixa-branca: técnicas para escolher casos de teste.

São classificações diferentes e complementares. Hoje começamos pela unidade menor: o teste unitário.

Ponto de partida

Por que começar por testes unitários?

Executam rápido e dão feedback enquanto a regra ainda está fresca.

Exercitam uma unidade pequena, com dependências controladas.

Deixam exemplos executáveis do comportamento esperado.

Não provam que o sistema inteiro funciona; integração e ponta a ponta também terão seu espaço.

Escolha dos casos

O que testar primeiro?

Caso esperado (caminho feliz): entrada válida e comum. Ex.: preço 100, desconto 10% → resultado 90.

Fronteiras / edge cases: valores nos limites e imediatamente ao redor deles, onde erros de comparação aparecem.

  • 0% e 100% → válidos; resultados 100 e 0.
  • 0% e 100% são inclusivos; -1% e 101% não são.

Entradas inválidas: dados ausentes, malformados ou fora do contrato da função. Ex.: preço -1 ou desconto 101% → erro claro (ValueError); na API, resposta 422.

Não existe uma ordem rígida para todo projeto: no TDD, comece com um comportamento pequeno — geralmente o caminho feliz — e acrescente fronteiras e inválidos conforme o contrato e o risco.

Test-Driven Development

O teste guia a implementação

TDD é uma prática de desenvolvimento: descrevemos um comportamento com um teste antes de implementar a solução.

  • Não é apenas escrever testes depois do código.
  • Não é perseguir uma porcentagem de cobertura.
  • Não elimina todos os bugs; ajuda a revelar falhas e proteger mudanças.

Um teste deve expressar um comportamento observável, não detalhes internos sem importância.

O ciclo

Red → Green → Refactor

1 · Red

Escreva um teste pequeno para um comportamento ainda não atendido. Rode e confirme que ele falha pelo motivo esperado.

2 · Green

Implemente somente o necessário para fazer o teste passar. Rode a suíte novamente.

3 · Refactor

Melhore a estrutura sem alterar o comportamento. Os testes devem continuar verdes.

Repita em passos curtos. Um vermelho sem motivo claro não é feedback útil: investigue-o.

Exemplo unitário · primeiro o teste

Desconto: qual comportamento queremos?

import pytest

from app.services.discount import calculate_discount


@pytest.mark.parametrize(
    ("price", "percentage", "expected"),
    [
        (100, 10, 90),
        (100, 0, 100),
        (100, 100, 0),
    ],
)
def test_calculates_discount(price, percentage, expected):
    result = calculate_discount(price, percentage)

    assert result == pytest.approx(expected)

O primeiro teste descreve o caminho feliz; os outros cobrem fronteiras importantes. Execute com pytest -q.

🟥 Se a função ainda não existe, a execução falha. Se existe como rascunho, a asserção deve falhar.

Green · primeira regra atendida

Implemente o mínimo

def calculate_discount(price: float, percentage: float) -> float:
    return round(price * (1 - percentage / 100), 2)

Os testes do caminho feliz e das fronteiras passam. Ainda não especificamos entradas inválidas: o próximo teste vai conduzir essa mudança.

Rode a suíte depois de cada passo. Verde confirma somente os comportamentos que os testes verificam.

Próximo ciclo · Red

Especifique entradas inválidas

import pytest


@pytest.mark.parametrize(
    ("price", "percentage"),
    [
        (-1, 10),
        (100, -1),
        (100, 101),
    ],
)
def test_rejects_invalid_values(price, percentage):
    with pytest.raises(ValueError):
        calculate_discount(price, percentage)

Rode pytest -q: o teste fica vermelho porque a função ainda aceita esses valores. Agora implemente somente a validação necessária.

Green · validação da regra

Faça os testes passarem

def calculate_discount(price: float, percentage: float) -> float:
    if price < 0:
        raise ValueError("O preço não pode ser negativo")
    if not 0 <= percentage <= 100:
        raise ValueError("O percentual deve estar entre 0 e 100")

    return round(price * (1 - percentage / 100), 2)

Rode todos os testes. Com tudo verde, refatore se houver uma melhoria clara sem mudar o comportamento observável.

Cada caso novo entrou porque havia um requisito — não para inflar a cobertura.

FastAPI · contrato da rota

Conecte a regra à API

from fastapi import FastAPI
from pydantic import BaseModel, Field

from app.services.discount import calculate_discount

app = FastAPI()


class DiscountRequest(BaseModel):
    price: float = Field(ge=0)
    percentage: float = Field(ge=0, le=100)


@app.post("/discount")
def discount(request: DiscountRequest) -> dict[str, float]:
    final_price = calculate_discount(request.price, request.percentage)
    return {"final_price": final_price}

O modelo valida os dados de entrada da requisição; a função mantém a regra de negócio testável de forma isolada.

FastAPI · teste de rota

Uma camada acima da unidade

from fastapi.testclient import TestClient

from app.main import app

client = TestClient(app)


def test_discount_endpoint_returns_final_price():
    response = client.post(
        "/discount",
        json={"price": 100, "percentage": 10},
    )

    assert response.status_code == 200
    assert response.json() == {"final_price": 90.0}


def test_discount_endpoint_rejects_invalid_percentage():
    response = client.post(
        "/discount",
        json={"price": 100, "percentage": 150},
    )

    assert response.status_code == 422

O TestClient exercita a rota, a validação da requisição e a resposta HTTP. É um teste de API/integração, não um teste unitário isolado.

Use-o depois de entender a regra com testes unitários rápidos e focados. Instalação para a prática: python -m pip install fastapi pytest httpx.

Prática e encerramento

Começamos pequeno. Evoluímos com confiança.

1. Escolha uma regra de negócio simples e escreva um teste unitário que falhe.

2. Faça-o passar com o mínimo de código; depois cubra fronteiras e entradas inválidas.

3. Refatore com os testes verdes; em seguida, teste o contrato da rota FastAPI.

Hoje: testes unitários primeiro. Depois: integração, API, sistema e aceitação conforme o risco e a necessidade.
